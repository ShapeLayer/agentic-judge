# 프론트엔드 기능 명세

UI 구현은 별도 작업자가 수행합니다. HTML/CSS, TypeScript, Web Components, Browser API를 사용합니다. 백엔드 HTTP API는 `POST /api/tools/{tool}`로 JSON 요청을 받으며 MCP와 동일한 요청·응답 모델을 사용합니다. Monaco와 수식 렌더러 등 모든 정적 자원·폰트·worker는 로컬 번들에 포함하고 CDN에 의존하지 않습니다.

## 탐색 및 문제 본문

`/problems`는 문제명·태그·제한·채점 준비 상태를 표시합니다. `/problems/[id]/`에는 문제 본문, 제출, 채점 결과, 채점 설정 네 탭을 둡니다. URL을 통해 선택한 탭과 제출·테스트 상세 화면의 상태를 복원합니다. `problem_get`의 legend/input/output/notes HTML을 섹션 제목과 함께 표시합니다. 원본 Markdown은 편집에 사용합니다. API가 반환하는 HTML은 정화되어 있지만 프론트엔드에서도 CSP를 적용합니다. 수식은 서버가 반환하는 MathML로 오프라인 렌더링합니다. 지원하지 않는 LaTeX는 원문으로 표시되므로 프론트엔드에서 로컬 KaTeX/MathJax로 렌더링을 보완할 수 있습니다. 예시 입력과 출력은 순서에 따라 쌍으로 표시하며, 복사 버튼을 제공하고 공백을 보존합니다. 예시 파일 개수는 manifest의 example_inputs/example_outputs와 일치시킵니다.

채점 준비 상태는 서버가 반환하는 ready 값을 기준으로 판단합니다. 정해 없음, 테스트 없음, 생성 실패, validator 거부, 변경으로 인한 답안 만료를 구분해 원인과 조치 버튼을 표시합니다. 정해 코드 저장 성공과 답안 생성 실패는 별개의 결과입니다. AI 검증을 수행하지 않았다는 이유로 채점 준비를 미완료 상태로 표시하지 않습니다.

## 제출

제출 탭 안에 Monaco 에디터/파일 첨부 전환을 둡니다. capabilities의 언어 목록과 파일 확장자를 연결하고 구문 강조, 줄 번호, 키보드 탐색, 변경 미저장 표시를 제공합니다. Browser File API로 UTF-8 파일을 읽어 `submit` source에 전달합니다. 브라우저는 서버의 파일 경로를 추측하지 않습니다. MCP에서는 workspace를 기준으로 한 상대 경로를 file에 지정하여 제출할 수 있습니다. 제출 전에 파일명·언어·코드 크기를 보여 줍니다. 에디터에 작성한 코드와 첨부 파일 중 선택한 하나만 전송합니다. 서버의 4 MiB 요청 제한을 고려합니다.

현재 API는 동기식입니다. 처리 중 버튼을 비활성화하고 작업 중임을 표시합니다. 시간 초과나 연결 끊김이 발생하면 재전송하기 전에 submissions_list로 제출 기록을 확인합니다. 장시간 전체 테스트 수행에 대비해 프록시 타임아웃을 조정합니다. 결과 도착 시 제출 ID를 기준으로 결과 탭의 해당 행을 엽니다. 결과 화면으로 전환해도 편집 중인 코드를 유지합니다.

## 채점 결과

submissions_list가 반환한 제출 목록을 생성 시간 역순으로 표시합니다. 각 행에 제출 시각, UUID, 언어, 종합 verdict, 통과/전체 테스트 수를 둡니다. 펼치면 suite, 순번, verdict, 실행시간, 메모리 측정값/측정 불가, stderr, checker 메시지를 표시합니다. CE는 컴파일 진단으로 표시하며 존재하지 않는 테스트 0번으로 연결되는 링크를 만들지 않습니다. CHECKER_ERROR는 사용자 오답과 다른 시스템 오류로 표현합니다. PE도 WA와 구분합니다.

실제로 실행한 각 테스트는 `/problems/[id]/tests/[suite]/[number]`에 연결합니다. 상세에는 입력·기대 출력·제출 출력, 공백 표시 전환, 복사/다운로드, 생성 기준, validator 근거, AI 검증 근거를 제공합니다. 과거 제출은 당시 generation과 cases의 input/expected_output 스냅샷을 표시하고 현재 테스트와 구분합니다. 큰 텍스트는 접거나 가상 스크롤합니다.

신뢰도는 확률이나 임의 퍼센트가 아닙니다. 현재 fingerprint와 일치하는 valid/invalid/uncertain/error 의견 수와 검사를 수행한 프로바이더·근거를 표시합니다. 미검증과 불확실·API 실패를 분리합니다. 이력 탭에서는 과거 리비전 검사도 읽되 현재 배지 계산에 포함하지 않습니다. 반대 의견이 하나라도 있으면 숨기지 않습니다. 해당 테스트를 검사한 근거가 없으면 정해에 대한 AI 의견만으로 테스트를 검증했다고 표시하지 않습니다.

## 채점 설정 (Polygon 기능)

1. 기본 정보: 제목, 태그, 시간/메모리 제한, suite 목록. 설정을 변경하면 생성된 출력이나 검증 결과가 만료될 수 있음을 실제 결과와 함께 표시합니다.
2. Statements: 네 Markdown 섹션 편집·수식 미리보기 및 예시 쌍 추가.
3. Answers: UUID·현재 revision·언어·expected AC/WA/RE/TLE/MLE·정해 여부 목록. 이름/파일명은 ID 대신 사용하지 않습니다. 코드 변경은 새 리비전으로 저장하고 이력 보기와 diff를 제공합니다. 정해 선택/수정 뒤 regeneration 결과를 표시합니다.
4. Validator: 저장된 answer UUID 선택 또는 해제. testlib validator 코드 편집은 answer_save, 연결은 settings_update. validator_run(input, expect_valid)으로 유효한 입력을 승인하고 무효한 입력을 거부하는지 테스트한 뒤 기록을 보여 줍니다.
5. Generator: 저장된 코드 UUID, 인수 배열, seed, 대상 suite/순번 입력; generate로 생성합니다. 인수를 shell command 문자열로 합치지 않습니다.
6. Checker: exact/tokens/lines 또는 내장 testlib 식별자, custom C++ source. custom 기본 경로는 evaluate/checker.cpp. 종료코드 _ok/_wa/_pe/_fail 의미를 설명하고 checker 자체 오류를 분리합니다.
7. Tests: suite별 번호·입출력·생성 상태·validator 결과·AI 검증 목록. 수동 입력(test_put), 생성기(generate), 전체 재생성(regenerate), 개별 상세(test_get)를 제공합니다.
8. Test runs: 저장된 각 answer의 expected와 실제 종합 결과를 비교합니다. AC로 지정한 풀이가 전체 테스트를 통과했는지, WA/RE/TLE/MLE로 지정한 풀이에서 의도한 실패가 관찰되었는지를 보여 줍니다. 시간/메모리 의존 실패는 현재 런타임에서만 유효합니다.
9. AI: 프로바이더별 검사 실행, 현재 리비전 근거와 과거 이력, 수정 방향 읽기. AI가 답안을 수정하는 버튼이나 코드를 자동으로 적용할 권한을 제공하지 않습니다. 사용자가 직접 수정하면 새 리비전이 됩니다.

## 상태·접근성·인수 조건

각 요청에 loading/empty/error/retry 상태를 정의합니다. 오류는 서버의 구체적 진단을 보존하되 키·인증 헤더를 노출하지 않습니다. 모든 동작은 키보드로 조작할 수 있어야 하고 테이블 펼침 상태는 aria-expanded로 표시합니다. verdict는 색만으로 전달하지 않습니다. 초기 화면은 오프라인에서 로드되어야 합니다. 외부 AI 연결이 실패해도 문제 조회와 로컬 채점은 가능해야 합니다. 저장소 경로와 컨테이너 사용 여부는 런타임 설정이며 문제 데이터 편집 화면의 임의 파일 접근 기능으로 노출하지 않습니다.

## UI 문체 및 모델 표시

설명·도움말·빈 상태·오류 안내·AI 검증 근거 등 사용자에게 보여 주는 한국어 줄글은 “~합니다/~습니다”체로 통일합니다. 버튼·탭·배지 등 짧은 명사형 레이블은 그대로 사용합니다. 사용자가 작성한 문제 본문·코드·외부 원문은 문체를 임의로 변경하지 않습니다. 안내 예시는 “정해가 없어 채점할 수 없습니다.”, “답안 생성을 완료했습니다.”, “모델 정보를 확인할 수 없습니다.”입니다.

AI 검증 목록과 상세에는 프로바이더와 모델명을 함께 표시합니다. response_model이 있으면 “응답 모델”로 표시하고, requested_model과 다르면 요청 모델도 함께 표시합니다. response_model이 없으면 requested_model을 “요청 모델”로 표시하고 “응답 모델 정보가 제공되지 않았습니다.”라고 안내합니다. 두 필드가 모두 없는 과거 기록은 “모델 정보가 기록되지 않았습니다.”라고 표시하며 현재 설정으로 추정하지 않습니다. 실패한 검증 기록에도 같은 표시 규칙을 적용합니다. 기록 API인 ai_review, reviews_list, trust_get은 두 필드를 그대로 반환합니다.
